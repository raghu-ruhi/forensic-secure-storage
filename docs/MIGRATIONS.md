# Database migrations (Flask-Migrate / Alembic)

The application **never creates or alters tables at startup**. Schema changes happen only through `flask db`.
Tests build their own throw-away schemas with `db.create_all()` (SQLite) and the migration tests use a temporary real
PostgreSQL - production schema management and test setup are separate.

## Revisions
| id | content |
|---|---|
| 0001 | baseline = the schema produced by the ORIGINAL code (autogenerated from the original models on PostgreSQL) |
| 0002 | OTP hardening columns, `evidence.mime_type`, `evidence.storage_backend`, `key_records.keygen_meta` (NOT NULL columns carry `server_default`, so it upgrades populated tables) |
| 0003 | `revoked_tokens` (logout) |
| 0004 | `users.mfa_last_used_step` (TOTP replay guard) |

## Commands (Windows CMD / Linux identical; run inside the backend container or the `backend` folder)
```
docker compose exec backend flask db current          # which revision is applied
docker compose exec backend flask db upgrade          # apply (the container entrypoint already does this on start)
docker compose exec backend flask db downgrade -1     # roll one revision back
cd backend && set FLASK_APP=run:app                   # local, CMD   (Linux: export FLASK_APP=run:app)
flask db migrate -m "describe change"                 # create a new revision after editing models
```
**Always read an autogenerated migration before applying it.** Autogenerate does not add `server_default` for new
NOT NULL columns (0002 needed hand-editing; the migration test fails without it) and cannot detect renames.

## Existing databases (created before migrations existed)
On start the entrypoint runs `app/migration_adopt.py`: if tables exist but `alembic_version` does not, it **only stamps**
the matching revision (0001 original release / 0002 OTP-fix release / 0003 / 0004 for `create_all` from current models)
and then `flask db upgrade` applies what is missing. Accounts and evidence rows are untouched (tested with data present).

## Rollback and recovery
* **Back up before upgrading:** `pg_dump -Fc forensic_db > backup.dump` (restore with `pg_restore`).
* `downgrade` drops the columns/tables added by that revision (data in them is lost; e.g. downgrading 0002 discards
  OTP hashes and `storage_backend` values - **do not downgrade past 0002 once evidence lives in S3**, the rows would no
  longer say where their objects are).
* Failed upgrade on PostgreSQL rolls the revision back (transactional DDL); fix and re-run.
